

# Test Execution & Observation Notes

## Maven & Command Options
- **Run all tests with safe timeout**: `mvn test "-Dsurefire.timeout=60"` (quotes required in PowerShell for `-D` flags with dots).
- **Run specific test class**: `mvn test -Dtest=WebSocketServerTest` (runs only that single class).

## Known Test Failures & Flakiness (Java-WebSocket commit `aad6654`)
- **`Issue941Test` Infinite Hang**: `pingLatch.await()` has no timeout annotation. If socket ping event fails to fire, JUnit hangs indefinitely. **Flaky, not guaranteed**: hung for 40+ min as test #55 in an overloaded shared TSVD4J process, but passed in 5s when run alone in a fresh process — points at TSVD4J's own overhead (see quadratic slowdown below) making the hang more likely, not the test being reliably broken.
- **`Issue962Test` / `Issue997Test` timeouts under TSVD4J**: both have a hard `@Test(timeout=2000ms)`. Pass normally; fail with `TestTimedOut` under TSVD4J field/API instrumentation because injected delays eat into the 2s budget. Same invasiveness pattern as `Issue825Test`.
- **`example.Autobahn*Test` (`AutobahnClientTest`, `AutobahnServerTest`, `AutobahnSSLServerTest`) are not real tests**: no `@Test` annotations, only a `public static void main(...)`. They're standalone demo programs living in `src/test` under the `example` package, meant to be run by hand against an external Autobahn test suite. Maven compiles them but JUnit finds 0 test methods and silently skips them — not a bug, not a gap in TSVD4J coverage.
- **`Issue825Test` Timeout**: `10s` sleep exceeds `15s` total test timeout under network/handshake delay.
- **`Issue847Test` Port Exhaustion**: Rapidly opening/closing 42 sockets causes Windows `ConnectException: Connection refused`.
- **`Issue256Test` Zombie Threads**: `ThreadCheck` fails when lingering worker threads from earlier failed/timed-out tests remain alive in the JVM.
- **Port-reuse cascade (baseline `mvn clean test`, JDK 8, no TSVD4J)**: a `WebSocketServer`-based test doesn't release its port before the next one binds it, throwing `BindException: Address already in use`. Once one test hits this, subsequent server tests on the same port fail too — a cascading, pre-existing flakiness source in the suite itself, unrelated to TSVD4J instrumentation. `WebSocketWorker-NNNN` thread names climbing into the thousands is just the JVM-wide naming counter, not itself evidence of a leak.

## TSVD4J Tool Bugs
- **0 tests ever run, every mode**: TSVD4J's plugin wraps its own agent jar path in literal quote marks, used both for `-javaagent` and as a classpath entry. Quote marks are illegal in Windows file paths, so Maven crashes before starting any test JVM — confirmed directly in `mvn -X` debug log (classpath entry shows `tsvd4j-core-0.1-SNAPSHOT.jar"` with a stray trailing quote, right before "Tests run: 0"). Affects `-Dapi`, `-Dfield`, and default — no command-line workaround exists. Fix described in `planning/TSVD4Jfix.md` (applied locally, one line, `TSVD4JMojo.java:79`).
- **Quadratic slowdown (not a hang)**: TSVD4J keeps several lists (`threadCountList`, `dangerousTPPairs`, `conflictingListPair`) that grow forever and are searched with `.contains()` on every single interception point. Cost per operation grows with everything seen so far → O(n²) overall. Measured: one forked JVM burned 14,776 CPU-seconds in ~79 minutes (saturating ~3 cores, not blocked) while stuck on test #55 of a shared-process run. First 30 simple classes finished in 34s total; by class 55 progress had stopped entirely. Fix: `-DreuseForks=false` (fresh JVM per class resets the lists) — this is what actually solved the stall, not a bigger timeout.

- **`-Dsurefire.timeout` does not work through the TSVD4J plugin**: set to 2700 (45 min), but `Issue941Test` sat stuck for **3h15m** before being killed manually. The flag is silently ignored — likely because TSVD4J re-invokes Surefire itself rather than Maven running it normally. **Do not rely on it as a hang safety net**; the only thing that reliably works is excluding known-bad classes with `-Dsurefire.excludes` / `-Dtest=` up front.
- **`Issue941Test` hang is position-dependent, not random**: hung at class 54 in the API run, hung again at class 54 in the field run, but passed in 5s when run alone in a fresh process. Suggests accumulated state/load late in a run — not the test being inherently broken.
- **`-DreuseForks=false` can't reset state inside a suite class**: `AllTests`/`AllIssueTests`/etc. are each *one* Surefire-level class internally running dozens of JUnit test classes via `@Suite.SuiteClasses`. Surefire only resets forks *between* its own classes, so the quadratic-slowdown bug (leaking static lists) gets an uninterrupted run through the whole suite before any reset happens. Observed during Stage D: `AllTests` ran first (alphabetical) and took a long time, mostly spent inside TSVD4J's own injected sleeps rather than genuinely stuck (confirmed via near-zero CPU growth over several minutes, contrasted with the CPU-saturated quadratic-blowup signature from Stage A). See [tsvd4j_known_issues.md](findings/tsvd4j_known_issues.md) issue 14.
- **False positive confirmed: TSVD4J flags `ConcurrentHashMap.put()` as a conflicting pair**, despite that class being specifically designed to be safe for exactly this pattern (many threads calling `.put()` at once, no external locking needed). Tested directly in `tsvd4j-sanity`: `synchronized`-protected writes and non-overlapping threads were both correctly left silent, so the tool isn't just over-eager everywhere — it specifically doesn't know which collection classes are already thread-safe. 1 of 3 tested "should be safe" patterns produced a false alarm. See [tsvd4j_known_issues.md](findings/tsvd4j_known_issues.md) issue 15.
- **Checked whether Java-WebSocket itself gives real-world evidence for that false-positive gap — it doesn't.** Went back through the actual 18 (Stage D) and 22 (Stage C) pairs already found on this project: every single one involves the project's own classes (`WebSocketClient`, `WebSocketImpl`, `Draft_6455`, `Opcode`, etc.), none touch a `java.util.concurrent` class. So this project is a dead end for turning the `ConcurrentHashMap` finding into a real-world (not just synthetic) result — a different project, one that actually uses `ConcurrentHashMap`/`Vector`/etc. heavily, would be needed instead. See [research_gaps.md](findings/research_gaps.md) Gap 1.
- **`marine-api` (chosen specifically because it genuinely uses `ConcurrentHashMap`) found 0 pairs in both API-only and field-only mode** — an inconclusive, not negative, result. Confirmed the agent genuinely ran (field mode took 185× longer than baseline, proving the delays were firing) rather than silently failing, so this isn't another instrumentation bug — TSVD4J just didn't catch anything here. Same "0 pairs despite real activity" symptom already flagged for `openpojo`, but that project's leading theory (reflection defeating the instrumenter) doesn't apply here, so the cause is still unknown. See [tsvd4j_findings.md](findings/tsvd4j_findings.md) run 2026-09-05-09.
- **`marine-api` Stage D (both trackers) also found 0 pairs — 3 for 3 zero across all three modes**, against the paper's 4/1/5. 36m29s runtime, `BUILD SUCCESS`, no hang. This is now a second project (alongside `openpojo`) where TSVD4J finds nothing at all despite the paper reporting real results — different suspected cause each time (reflection for `openpojo`, unknown for `marine-api`). Dead end for the original `ConcurrentHashMap` false-positive question on this project; a third candidate or repeated runs are the next options.
- **Repeated all 3 modes on `marine-api` a second time, independently — same result, 6 for 6 zero.** Timing matched run 1 almost exactly for every stage (3m25s/33m54s/36m25s vs run 1's ~2min/33m56s/36m29s), which rules out "one unlucky run." `marine-api` consistently, reproducibly produces nothing for TSVD4J — a confirmed dead end for the false-positive question, and stronger evidence for the reproducibility concern in issue 16.
- **New project (`commons-dbcp`), Stage A hit the quadratic-slowdown bug on the very first class** — a fresh JVM, no accumulated history, yet 2326 CPU-seconds burned in ~19 minutes with zero progress. Cause found in the test source itself: `TestDriverAdapterCPDS` spins up 200 real threads doing 5000 connection-pool operations each (1,000,000 total), directly hammering the exact `ConcurrentHashMap` fields (`pcMap`/`validatingSet`) we picked this project to test. Had to exclude the class — it will never finish under instrumentation. Refines issue 2: the trigger is total operation count, not number of classes run. Ironic downside: this was probably the single best real-world candidate yet for the `ConcurrentHashMap` false positive, and it's now unrunnable. See [tsvd4j_findings.md](findings/tsvd4j_findings.md) run 2026-09-06-10.
- **BREAKTHROUGH: the `ConcurrentHashMap` false positive is now confirmed on real, unmodified production code.** With the two problem classes excluded, Stage A on `commons-dbcp` completed and found 6 conflicting pairs — 3 of them directly on `validatingSet`/`pcMap` (both `ConcurrentHashMap`-backed), via three different operation pairs (`contains`×`remove`, `get`×`put`, `remove`×`remove`). Verified directly in source: every flagged line is exactly the kind of concurrent access `ConcurrentHashMap` is built to make safe. This is the exact real-world result `marine-api` failed to produce twice — Gap 1 in [research_gaps.md](findings/research_gaps.md) is now answered, not just theorized. See [tsvd4j_findings.md](findings/tsvd4j_findings.md) run 2026-09-06-11.
- **Checked the other 3 pairs too — all 6 confirmed false positives, not just 3.** The remaining 3 pairs belonged to `commons-pool2` (a separate Apache library `commons-dbcp` depends on internally), not `commons-dbcp` itself. Cloned that library's exact matching version to check properly: its `allObjects` field is also a `ConcurrentHashMap`. So this one run found the same mistake across **two independent codebases**, 3 different fields, and every basic map/set operation (`get`/`put`/`remove`/`contains`) — a 100% false-positive rate on this run's 6 reported pairs. Full code for all 6: [six_pairs_explained.md](findings/six_pairs_explained.md).

## TSVD4J Stage D Result — Java-WebSocket, default mode (both trackers, 70/71 classes)
- **18 distinct conflicting pairs** (34 raw), vs paper's 25. Ran clean in **1h14m**, `BUILD SUCCESS`, no interruption — ~28× the 2m36s baseline. 628 tests over 70 classes; `Issue941Test` excluded up front.
- **Unexpected: default mode found FEWER pairs than field-only did** (18 vs Stage C's 22), despite watching strictly more (API + field together). 4 of Stage C's pairs vanished, 3 new ones appeared (`Draft_6455:269→HandshakeState:14`, `Draft_6455:728→805`, `Issue598Test:164→Opcode:7`). Most likely TSVD4J's own non-determinism — but it means **I cannot assume default mode is a superset of field mode**, which is the intuitive expectation.
- **~20% of tests failed or errored** (14 failures + 111 errors of 628), far worse than Stage A/C's single digits. Worst case: `Issue847Test` errored on **42 of 42** tests. Doubling the injected-delay points (both trackers at once) is the clearest invasiveness evidence so far — a detector that breaks a fifth of the suite to get its answer has a cost Table II never shows.
- **`AllTests` alone ate 30 of the 74 minutes** (184 tests in one fork) — this is where the `-DreuseForks=false` suite-class limitation was first spotted live (see bullet above / known issue 14).

## TSVD4J Stage C Final Result — Java-WebSocket, field mode (70/71 classes, closed out)
- **Final: 22 distinct conflicting pairs**, vs paper's 25. `Issue941Test` excluded — hung 3/3 attempts when run alongside other work, but passed in 5s the one time it ran completely alone on an idle JVM. Not simple 50/50 flakiness — looks load-dependent.
- **How to tell "hung" from "slow" reliably**: check CPU-seconds used vs wall-clock time elapsed. The quadratic-slowdown hang (see below) burns CPU constantly (~3 cores maxed). This hang used **~1-2% CPU** over 15 minutes — near-total silence — meaning it's blocked waiting on something that never arrives (matches `pingLatch.await()` with no timeout), not grinding through a slow computation. Different symptom, different cause, same "looks stuck" surface appearance.
- **Accidental interruptions happened 3 times total this session** (`Ctrl+C` while trying to copy log text mid-run) — each time recognizable by `java.lang.InterruptedException: sleep interrupted` appearing in the log right at TSVD4J's own delay call. One instance also triggered a `NoClassDefFoundError` for TSVD4J's own `Proxy` class shortly after — the interruption may leave the JVM's classloading in a bad state, though the run recovered and completed anyway.

## TSVD4J Stage C Result — Java-WebSocket, field mode (partial, 54/71 classes)
- **22 distinct conflicting pairs found** (38 raw before dedup — `-DreuseForks=false` makes TSVD4J re-report the same pair per fork). Paper's Table II reports **25** for this project in field-only mode, so 22 with 17 classes still unrun is tracking close.
- **All pairs are in project source, clustered at 5 sites**: `WebSocketClient:75`, `WebSocketClient:526`, `Draft_6455:809`, `Draft_6455:810`, `WebSocketImpl:596` — each conflicting against many different lines. Looks like a few shared fields touched from many places, not 22 unrelated bugs.
- **Only 9 test methods triggered them**, all in reconnect/close/stop scenarios (`Issue256Test`, `Issue580Test`, `Issue879Test`) — i.e. shutdown-path concurrency.
- **Field mode was faster than expected**: 54 classes in ~37 min, much better than API mode's first (pre-`reuseForks=false`) attempt. Using `-DreuseForks=false` from the start is what made the difference.

## TSVD4J Stage A Result — Java-WebSocket, API-only mode
- **71 of 71 real test classes completed, 0 conflicting pairs found.** (74 files total minus the 3 non-test `Autobahn*` files above = 71 actual tests.) Matches the paper's Table II value of 0 for API-only tracking on this project.
- Required splitting the run into 3 batches (`-Dtest=` subsets) with `-DreuseForks=false` + `-Dsurefire.timeout=600` to work around the quadratic slowdown; a single unbroken run never finished.
